Data Architecture Overview

Oct 04, 202622 min read

Apache Data Formats 데이터 관련 아파치 재단 오픈소스들에 대해 공부하다가 다시 빅데이터 아키텍처에 대해 복습

Abstract

빅데이터 아키텍처들은, “어떻게 하면 방대한 양의 데이터를 정확하게, 혹은 지연 시간 없이 실시간으로 처리하고 보여줄 수 있을까?” 라는 문제에 대한 해결책으로서 발전되어왔다.

요구사항의 성격에 맞게 데이터 처리 레이어를 분리하고, 결과는 합쳐서 보여준다.

  • 배치 레이어(정확도) + 스피드/스트리밍 레이어(실시간)
  • 서빙 레이어(처리된 데이터)

초기 하둡 시절 빅데이터 인프라는 배치 처리 중심이었음 (Like 옵스나우 CUR 데이터를 스파크에서 밤새 몇 시간 걸려서 배치처리하던 것 처럼)

배치는 전체 데이터를 다시 계산하므로 정확하지만, 한 번 도는 데 몇 시간이 걸려서 그 사이에 들어온 최신 데이터는 결과에 없다. 그래서 스피드 레이어가 “마지막 배치 이후에 들어온 데이터”만 빠르게 계산해 그 공백을 메우고, 다음 배치가 끝나면 그 구간은 배치 결과로 대체된다.

OSS

Kafka (Broker)

분산 이벤트 스트리밍 플랫폼, 원천 데이터의 통로로서 배치, 스피드 레이어 양쪽에서 가져갈 수 있도록 하는 역할

Spark (Batch Processing)

HDFS/S3에 적재된 대규모 데이터를 주기적으로 정확하게 계산

Spark / Storm (Stream Processing)

Kafka에 produce된 데이터를 초 단위로 빠르게 집계

Parquet

배치에서 정제된 데이터를 디스크에 적재할 때 쓰는 열 기반 파일 포맷. 분석 쿼리(OLAP)는 일부 컬럼만 읽는 경우가 많아서 열 기반 포맷이 유리하다.

Druid / Pinot (Serving)

스피드 레이어의 실시간 결과와 배치 레이어의 과거 결과를 묶어 사용자에게 응답하기 위한 서빙 데이터를 제공

단점

‘유지보수성’.
결국 같은 집계 로직을 배치용과 실시간용으로 각각 따로 개발하고 유지보수해야한다. 두 구현의 결과가 서로 어긋나지 않게 맞추는 것도 부담이다.

OSS

Kafka (Broker+Storage)

‘이벤트 스트리밍 플랫폼’ 역할 뿐만 아니라, 중장기간(ex. 몇 주치) 대규모 원본 데이터를 보관하는 저장소 역할까지 겸한다.

Flink (Stream Processing)

Lambda 아키텍처처럼 배치, 스트림 프로세싱처리 로직을 이분화할 필요 없이, Flink 하나로 Kafka Topic의 데이터를 실시간 처리와 과거 데이터 재처리(Backfill)에 동일 로직을 적용할 수 있다.

단점

‘저장소로서의 Kafka의 한계’
재처리(Reprocessing)을 위해서는 Kafka에 보관된 과거 데이터스트림을 처음부터 재생해서 처리 파이프라인을 태워야한다.
이론적으로는 문제 없을지라도 본디 ‘이벤트 스트리밍 플랫폼’ 역할인 Kafka는 장기간의 PB급 원본 데이터를 저장하기에는 브로커 디스크 비용과 운영 부담이 크다. (최근에는 오래된 데이터를 S3로 내리는 Tiered Storage 기능으로 이 한계가 일부 완화됨)
또한 Kafka는 순서대로 읽는 로그 구조라서, OLAP 처럼 SQL을 통해 분석 쿼리(Ad-hoc)를 하기 위해 만들어지지 않음

저렴한 클라우드 스토리지(데이터 레이크, ex. S3) + 데이터 웨어하우스의 관리 기능(트랜잭션, 스키마 관리)을 결합한 형태

  • 스토리지: S3 등의 데이터레이크로 일원화
  • 테이블 포맷: 데이터레이크에 오픈 테이블 포맷 을 얹어 스트림, 배치 처리 시 하나의 저장소를 Read/Write할 수 있게 한다.
  • 다이어그램의 Bronze → Silver → Gold는 메달리온 아키텍처라고 부르는 관례로, 같은 저장소 안에서 데이터를 원시 → 정제 → 집계 단계로 나누어 관리하는 방식이다.

“처리 엔진(Flink/Spark)은 용도에 맞게 쪼개 쓰되, 데이터는 저렴하고 무한한 S3 한 곳에 다 모으고, Iceberg로 질서를 부여하자”

vs Lambda

레이크하우스에도 배치와 스트림 경로가 둘 다 있어서 람다와 비슷해 보인다. 하지만 람다처럼 동일한 데이터를 두 번 처리하는 것이 아니라, 데이터가 도착하는 운송 수단만 다른 것이다.

람다는 배치 데이터와 실시간 스트림 데이터의 저장소(ex. Redis vs HDFS)가 이분화되어있었다. 결과적으로 실시간 뷰와 배치 결과 뷰를 조회하기 위한 로직이 달라지고, 두 저장소의 데이터를 합쳐서 보여주기 위해서는 어플리케이션에서 복잡한 쿼리를 작성해야했다.

데이터레이크하우스에서는 S3 윗단 Iceberg와 같은 단일 목적지에 실시간, 배치 데이터가 전부 저장되며, 데이터 운송 수단(ex. Kafka & Flink vs Spark)만 달라진다.
표준화된 테이블 포맷(Iceberg)을 뒀기 때문에, 어느 방식으로 데이터가 도착했든 쿼리 엔진(Athena, DuckDB)는 하나의 SQL쿼리로 데이터를 JOIN/AGG 할 수 있다.
즉, 따로 저장된 데이터 유형으로 인해 어플리케이션에서 복잡한 쿼리를 작성할 필요가 없어졌다.

OSS

Iceberg (Open Table Format)

by Netflix. 스토리지 위의 소프트웨어 규칙.
S3에는 Parquet 파일들이 흩어져 있을 뿐이다. Iceberg는 “지금 이 테이블은 어떤 파일들로 이루어져 있는가”를 파일 목록과 통계 정보를 기록한 메타데이터 파일로 관리한다. 쿼리 엔진은 스토리지를 직접 뒤지지 않고, 이 메타데이터를 먼저 읽어서 필요한 파일만 골라 읽는다.

파이프라인의 핵심
Flink가 스트리밍 데이터를 처리해서 스토리지에 저장하는 와중에도 Spark와 같은 배치 엔진이 기존 데이터를 안전하게 읽거나 덮어쓸 수 있도록 트랜잭션(ACID)을 보장해준다. 쓰기가 끝날 때마다 새 메타데이터 파일(스냅샷)을 만들고 “현재 스냅샷”을 한 번에 바꿔치기하는 방식이라서, 읽는 쪽은 쓰다 만 중간 상태를 볼 일이 없다.

같은 역할의 포맷으로 Delta Lake(Databricks), Hudi(Uber)가 있다.

Parquet (Storage Format)

S3 데이터 적재 포맷. 실제 데이터는 Parquet 파일에 들어 있고, Iceberg는 그 파일들을 테이블로 묶는 역할이다.

Kafka & Flink (Data Ingestion & Streaming)

외부 원천 데이터를 실시간으로 받아 Iceberg 테이블로 지속적으로 적재

Spark (Batch / ETL)

쌓여있는 Iceberg 테이블을 읽어 잘못된 부분 수정 / 대규모 JOIN / AI 학습용 피처 생성 등의 무거운 배치성 작업을 수행

Arrow (In-memory Format)

열 기반 인메모리 데이터 포맷의 표준. DuckDB, Spark, ML 라이브러리가 메모리 위에서 같은 형식을 쓰기 때문에, 엔진 사이에 데이터를 넘길 때 변환(직렬화/역직렬화) 비용이 거의 들지 않는다. Parquet이 디스크 저장용이라면 Arrow는 메모리 연산용이다.

Airflow

배치 작업, 테이블 최적화(Compaction: 잘게 쪼개져 쌓인 작은 파일들을 큰 파일로 병합) 등의 순서를 조율

Streaming Lakehouse

기존 Lakehouse의 한계: 분 단위 지연

Parquet은 한 번 쓰면 수정할 수 없는 파일이라서, 데이터가 한 건 들어올 때마다 파일을 만들 수 없다. 그래서 일정량의 데이터를 모았다가 한 번에 파일로 쓰고 테이블에 반영(commit)한다. 이렇게 짧은 주기로 모아서 쓰는 방식을 Micro-batch라고 부르며, 이 주기만큼(보통 분 단위) 지연시간이 발생한다. 주기를 줄이면 작은 파일이 너무 많이 생겨서 조회 성능이 떨어진다.
→ 초 단위 실시간 형태로 보완 필요

보완

  • 데이터가 들어오는 즉시, 쓰기가 빠른 로그 형태(뒤에 이어 붙이는 Append 방식)로 먼저 기록한다.
    • Apache Hudi(우버)의 Merge-on-Read 테이블, Apache Paimon(알리바바, Flink 진영)처럼 스트리밍 쓰기에 맞춰 설계된 포맷이 이 방식을 쓴다.
  • 백그라운드에서 로그를 조회에 유리한 Parquet 파일로 별도 변환(Compaction)한다.
  • 조회할 때는 엔진이 “Parquet + 아직 변환되지 않은 로그”를 합쳐서 읽기 때문에 최신 데이터까지 보인다.
  • 기존에는 Kafka로 들어온 실시간 데이터와 S3의 과거 데이터를 별도 조회해서 애플리케이션 단에서 통합해야했음(Lambda의 잔해)
    • 하나의 테이블에 대한 하나의 SQL로 실시간 데이터와 과거 데이터를 함께 조회 가능
  • 다만 지연시간은 초~분 단위까지 줄어드는 것이고, ms 단위가 필요하면 여전히 Kafka 같은 로그 시스템을 직접 읽어야 한다.

조직과 메타데이터 관점의 아키텍처

여기까지는 “데이터를 한 곳에 모아 어떻게 저장하고 처리할 것인가”에 대한 아키텍처였다. 아래 둘은 성격이 다르다. 저장/처리 기술이 아니라, 회사 규모가 커져 데이터와 조직이 여러 갈래로 나뉘었을 때 누가 어떻게 관리할 것인가에 대한 접근법이다.

Data Mesh

by Zhamak Dehghani (Thoughtworks, 2019)
‘조직 & 도메인’ 중심 분산 아키텍처

‘데이터 엔지니어링 팀’과 같은 소수 인원의 중앙 팀이 전사 데이터를 모두 관리하면, 그 팀이 병목이 된다. 결제, 추천, 마케팅 데이터는 각각 의미와 특성이 다른데 중앙 팀은 모든 도메인을 깊이 알 수 없고, 모든 요청이 한 팀에 몰리기 때문이다.

그래서 MSA처럼 각 비즈니스 도메인(ex. 결제, 추천, 마케팅 등) 팀이 자기 데이터를 직접 소유하고 관리하도록 분산시킨다. 아래 원칙들로 구성된다.

Data as a Product

  • 도메인 팀은 자기 데이터를 다른 팀이 바로 쓸 수 있는 “제품”처럼 다룬다. 즉, 정제하고 문서화해서 품질을 책임진 상태로 사내 데이터 플랫폼에 공개(Produce)한다.
  • 이 데이터가 필요한 다른 도메인에서 가져다 쓰는(Consume) 형태

Self-serve 인프라

  • 즉, 사내 데이터 플랫폼. 도메인 팀마다 인프라를 처음부터 만들 수는 없으므로, 중앙 데이터 팀은 데이터를 직접 관리하는 대신 플랫폼(저장소/파이프라인 템플릿, 카탈로그, 권한 관리 등)만 제공한다.

Federated Governance

  • 분산시키더라도 보안, 명명 규칙, 데이터 포맷 같은 공통 규칙은 전사 차원에서 정하고, 가능하면 플랫폼이 자동으로 강제한다. 이게 없으면 도메인마다 제각각이 되어 서로의 데이터를 쓸 수 없다.

사용 기술

  • 도메인별 작은 ‘Lakehouse’
  • 도메인 간 공유를 위한 프로토콜 / API / 데이터 카탈로그

Data Fabric

Gartner 등이 정립한 개념. ‘메타데이터 기반’ 통합

기업의 데이터는 여러 클라우드, 온프레미스, SaaS(CRM 등)에 물리적으로 흩어져 있다. 데이터 메시가 이 문제를 “조직과 책임을 나누는 것”으로 푼다면, 데이터 패브릭은 “기술 계층을 하나 얹는 것”으로 푼다.

데이터 패브릭은 물리적으로 분산된 데이터를 옮기지 않고, 그 위에 가상의 통합 계층(패브릭)을 두어 하나처럼 조회하고 관리한다.

핵심은 메타데이터(데이터에 대한 데이터: 어디에 어떤 테이블이 있고, 누가 쓰고, 어디서 만들어졌는지)다.

  • Active Metadata: 카탈로그에 적어두기만 하는 수동적인 메타데이터가 아니라, 쿼리 로그나 사용 패턴 등을 계속 수집해서 갱신되는 메타데이터
  • 지식 그래프: “이 CRM의 고객 ID와 저 Lakehouse의 user_id는 같은 것”처럼 데이터 간의 관계를 연결해 둔 것
  • 이 둘 위에 AI/ML을 얹어서 데이터 탐색, 연결, 통합 작업을 자동화하는 것을 지향한다.

ex) 작년 우수 고객 명단 조회 → 패브릭 계층이 메타데이터를 보고 Lakehouse, CRM, Log 중 어디에 관련 데이터가 있는지 찾아 연결해서 조회

대신 고도화된 메타데이터 관리 솔루션(Atlan, Alation 등 데이터 카탈로그)과 분산 쿼리 엔진(Starburst/Trino 등)이 필요하다. 특정 제품이라기보다 지향점에 가까운 개념이라, 실제 자동화 수준은 솔루션마다 차이가 크다.

메시와 패브릭은 한쪽이 다른 쪽을 대체하는 관계가 아니다. 메시는 조직 운영 방식이고 패브릭은 기술 계층이라서 함께 쓸 수 있다.

진화 과정

결론적으로,

  1. 정확한 배치 결과에 더해 실시간 데이터도 조회해야 한다 (Lambda)
  2. 로직의 중복을 줄인다 (Lambda → Kappa)
  3. 저장소를 저렴한 오브젝트 스토리지 하나로 통일하고, 컴퓨팅 엔진은 분리해 용도별로 쓴다 (Kappa → Lakehouse)
  4. 통일된 저장소의 지연시간을 줄인다 (Lakehouse → Streaming Lakehouse)
  5. 데이터 중앙화로 인한 조직의 병목을 해소하기 위해 도메인별로 소유권을 나눈다 (Data Mesh)
  6. 흩어진 데이터를 메타데이터 계층으로 연결한다 (Data Fabric)

의 단계로 진화해온 것으로 보인다. 14는 저장/처리 기술의 흐름이고, 56은 그 위에서 조직과 관리 방식을 다루는 별도의 축이다.
